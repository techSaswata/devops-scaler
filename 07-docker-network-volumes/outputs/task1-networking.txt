==================== 3. ADD THE BACKEND CONTAINER TO A SECOND NETWORK ====================
A container can only join ONE network with 'docker run --network'.
Additional networks are attached afterwards with 'docker network connect'.

$ docker network connect frontend-net backend
connected.

--- proof: backend now has TWO network interfaces ---
$ docker inspect backend --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} -> {{$v.IPAddress}}{{println}}{{end}}'

############ 6b. backend -> database  (share backend-net) ############

64 bytes from database.backend-net (172.20.0.2): icmp_seq=3 ttl=64 time=0.147 ms

--- database ping statistics ---

$ docker exec backend nc -zv database 3306

--- an actual SQL query across the network ---
$ docker exec backend mysql --skip-ssl -h database -uappuser -papppass appdb -e 'SELECT ...'
result	mysql_version
backend reached the database over backend-net	8.0.46
>> SUCCESS — real MySQL protocol traffic between two containers.

############ 6c. frontend -> database  (share NO network) ############
$ docker exec frontend ping -c 2 database    (expected to FAIL)
ping: bad address 'database'

$ docker exec frontend getent hosts database   (expected: nothing)
(no result — name does not resolve)

>> FAILS, and this is the POINT. frontend and database share no network,
>> so Docker's DNS will not even resolve the name for them. The database
>> is unreachable from the public-facing tier — network segmentation.

############ 6d. frontend -> backend  (share frontend-net) ############
$ docker exec frontend ping -c 2 backend
64 bytes from 172.19.0.3: seq=1 ttl=64 time=0.215 ms

--- backend ping statistics ---
2 packets transmitted, 2 packets received, 0% packet loss
round-trip min/avg/max = 0.038/0.126/0.215 ms
>> SUCCESS — the backend is the only bridge between the two tiers.
