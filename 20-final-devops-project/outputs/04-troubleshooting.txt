=== FAULT 1 of 6 - the pod never starts ===

--- IDENTIFY ---

$ kubectl get pods -n finalproject-broken
NAME                        READY   STATUS    RESTARTS   AGE
task-api-6bdd74c576-4zbt5   0/1     Pending   0          11s
>> Pending. Not Running-and-broken: never scheduled onto a node at all.

--- INVESTIGATE ---

$ kubectl describe pod -l app=task-api -n finalproject-broken | sed -n '/^Events:/,$p'
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  11s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint(s), 2 Insufficient cpu. preemption: 0/3 nodes are available: 3 Preemption is not helpful for scheduling.

--- ROOT CAUSE ---
  FailedScheduling: 'Insufficient cpu' on the 2 workers, and the
  control-plane is excluded by its own taint. The container requests 16
  CPUs:

$ kubectl get deploy task-api -n finalproject-broken -o jsonpath='requests: {.spec.template.spec.containers[0].resources.requests}{"\n"}'
requests: {"cpu":"16","memory":"48Mi"}

$ kubectl get nodes -o custom-columns='NODE:.metadata.name,ALLOCATABLE_CPU:.status.allocatable.cpu' --no-headers
devops-hw-control-plane   6
devops-hw-worker          6
devops-hw-worker2         6
  6 allocatable per node < 16 requested. A request is a SCHEDULING
  contract: the scheduler will not overcommit it, so no node qualifies
  and the pod waits forever rather than starting and being throttled.

--- FIX ---

$ kubectl patch deployment task-api -n finalproject-broken --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/resources/requests/cpu","value":"100m"},{"op":"replace","path":"/spec/template/spec/containers/0/resources/limits/cpu","value":"500m"}]'
deployment.apps/task-api patched

--- VERIFY ---

$ kubectl get pods -n finalproject-broken
NAME                        READY   STATUS         RESTARTS   AGE
task-api-6bdd74c576-4zbt5   0/1     Pending        0          23s
task-api-7c995f644-4w95l    0/1     ErrImagePull   0          12s
>> Scheduled now, and the next fault is already visible.

=== FAULT 2 of 6 - scheduled, but no image ===

--- IDENTIFY ---

$ kubectl get pods -n finalproject-broken --field-selector=status.phase!=Succeeded
NAME                        READY   STATUS         RESTARTS   AGE
task-api-6bdd74c576-4zbt5   0/1     Pending        0          23s
task-api-7c995f644-4w95l    0/1     ErrImagePull   0          12s
>> ErrImagePull / ImagePullBackOff on the new ReplicaSet's pod.

--- INVESTIGATE ---

$ kubectl describe pod -n finalproject-broken -l app=task-api | grep -E 'Failed to pull|Error: Err|Back-off' | head -4
  Warning  Failed     6s    kubelet            Failed to pull image "task-api:1.0.1": failed to pull and unpack image "docker.io/library/task-api:1.0.1": failed to resolve reference "docker.io/library/task-api:1.0.1": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
  Warning  Failed     6s    kubelet            Error: ErrImagePull
  Normal   BackOff    6s    kubelet            Back-off pulling image "task-api:1.0.1"

--- ROOT CAUSE ---

$ kubectl get deploy task-api -n finalproject-broken -o jsonpath='image: {.spec.template.spec.containers[0].image}{"\n"}'
image: task-api:1.0.1
  Tag 1.0.1 was never built. Only task-api:1.0.0 was imported into the
  nodes:

$ docker exec devops-hw-worker crictl images 2>/dev/null | grep -E 'IMAGE|task-api'
IMAGE                                                   TAG                  IMAGE ID            SIZE
docker.io/library/task-api                              1.0.0                3d4fdbc13cb63       43.7MB
  A bare name with no registry is resolved as docker.io/library/task-api,
  so the kubelet asks Docker Hub for a repository that does not exist --
  which is why the error says 'pull access denied' rather than 'no such
  tag'. Hub will not confirm the absence of a private-looking repo.

--- FIX ---

$ kubectl set image deployment/task-api api=task-api:1.0.0 -n finalproject-broken
deployment.apps/task-api image updated

--- VERIFY ---

$ kubectl get pods -n finalproject-broken --field-selector=status.phase!=Succeeded

task-api-5dcdc9cfc-8wnms   0/1     CreateContainerConfigError   0          12s
task-api-7c995f644-4w95l   0/1     ImagePullBackOff             0          25s

=== FAULT 3 of 6 - image pulled, container will not be created ===

--- IDENTIFY ---
>> CreateContainerConfigError. The image is fine; the kubelet cannot
>> assemble the container's configuration.

--- INVESTIGATE ---

$ kubectl describe pod -n finalproject-broken -l app=task-api | grep -E 'Error:|Warning' | head -5
  Warning  Failed     11s (x2 over 12s)  kubelet            Error: secret "task-api-secret" not found
  Warning  Failed     19s               kubelet            Error: ImagePullBackOff
  Warning  Failed     3s (x2 over 19s)  kubelet            Failed to pull image "task-api:1.0.1": failed to pull and unpack image "docker.io/library/task-api:1.0.1": failed to resolve reference "docker.io/library/task-api:1.0.1": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
  Warning  Failed     3s (x2 over 19s)  kubelet            Error: ErrImagePull

--- ROOT CAUSE ---

$ kubectl get deploy task-api -n finalproject-broken -o jsonpath='envFrom: {.spec.template.spec.containers[0].envFrom}{"\n"}'
envFrom: [{"configMapRef":{"name":"task-api-config"}},{"secretRef":{"name":"task-api-secret"}}]

$ kubectl get secret -n finalproject-broken
No resources found in finalproject-broken namespace.
  The Deployment pulls its environment from a Secret named
  task-api-secret, and no such Secret exists in this namespace. A
  secretRef is REQUIRED unless marked optional:true, so the kubelet
  refuses to start the container rather than running it with the
  credentials silently missing. That is the right default.

--- FIX ---
$ kubectl create secret generic task-api-secret --from-literal=...
secret/task-api-secret created

=== FAULT 4 of 6 - Running, but never Ready ===

--- IDENTIFY ---

$ kubectl get pods -n finalproject-broken -l app=task-api --field-selector=status.phase=Running
NAME                       READY   STATUS    RESTARTS   AGE
task-api-5dcdc9cfc-8wnms   0/1     Running   0          38s
>> STATUS Running with READY 0/1. The process is up; Kubernetes is
>> refusing to call it serviceable.

--- INVESTIGATE ---

$ kubectl describe pod task-api-5dcdc9cfc-8wnms -n finalproject-broken | grep -i 'readiness probe' | head -3
  Warning  Unhealthy  22s                kubelet            Readiness probe failed: Get "http://10.244.1.23:8000/healthz": dial tcp 10.244.1.23:8000: connect: connection refused
  Warning  Unhealthy  1s (x5 over 21s)   kubelet            Readiness probe failed: HTTP probe failed with statuscode: 404

--- ROOT CAUSE ---

$ kubectl get deploy task-api -n finalproject-broken -o jsonpath='readiness path: {.spec.template.spec.containers[0].readinessProbe.httpGet.path}{"\n"}'
readiness path: /healthz
  The probe asks for /healthz. This app serves /health and /ready --
  /healthz is Go-ecosystem convention, not this application's API. The
  404 counts as a probe failure, so the pod is held out of the Service
  endpoints. Proof the app itself is healthy on its real paths:

$ GET /health  from inside the pod
{"status": "healthy"}
$ GET /healthz from inside the pod
FAILED: HTTPError HTTP Error 404: Not Found
>> The probe was right to fail. The PATH was wrong, not the app.

--- FIX ---

$ kubectl patch deployment task-api -n finalproject-broken --type=json -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/ready"}]'
deployment.apps/task-api patched

--- VERIFY ---

$ kubectl get pods -n finalproject-broken -l app=task-api --field-selector=status.phase=Running
NAME                        READY   STATUS        RESTARTS   AGE
task-api-5dcdc9cfc-8wnms    0/1     Terminating   0          64s
task-api-74d8d9564b-n6pzn   1/1     Running       0          25s
>> 1/1 READY.

=== FAULT 5 of 6 - a healthy pod that nothing can reach ===

--- IDENTIFY ---
$ GET / through the Service DNS name
FAILED: URLError <urlopen error [Errno 111] Connection refused>
>> Name resolves, connection goes nowhere. The pod is 1/1 Ready.

--- INVESTIGATE ---

$ kubectl get endpoints task-api -n finalproject-broken
NAME       ENDPOINTS   AGE
task-api   <none>      89s
>> ENDPOINTS <none>. The Service has no backends, so there is nothing
>> for kube-proxy to forward to. Compare what it SELECTS with what the
>> pod actually CARRIES:

$ kubectl get svc task-api -n finalproject-broken -o jsonpath='service selector: {.spec.selector}{"\n"}'
service selector: {"app":"taskapi"}

$ kubectl get pod task-api-5dcdc9cfc-8wnms -n finalproject-broken -o jsonpath='pod labels:       {.metadata.labels}{"\n"}'
pod labels:       {"app":"task-api","pod-template-hash":"5dcdc9cfc"}

--- ROOT CAUSE ---
  selector app=taskapi, label app=task-api. One hyphen. A Service builds
  its endpoint list purely by label match, and there is no warning event
  for a selector that matches nothing -- the Service is reported as
  perfectly healthy. This is why 'the pod is Running' is never enough
  evidence that a service works.

--- FIX ---

$ kubectl patch svc task-api -n finalproject-broken --type=json -p='[{"op":"replace","path":"/spec/selector/app","value":"task-api"}]'
service/task-api patched

--- VERIFY ---

$ kubectl get endpoints task-api -n finalproject-broken
NAME       ENDPOINTS          AGE
task-api   10.244.1.24:8080   96s
>> An endpoint exists now, so the label fix worked. Read the PORT on it
>> before celebrating -- the next request still fails identically.

=== FAULT 6 of 6 - an endpoint that points at the wrong port ===

--- IDENTIFY ---
$ GET / through the Service DNS name
FAILED: URLError <urlopen error [Errno 111] Connection refused>
>> Byte for byte the SAME error as fault 5: Errno 111, connection refused.
>> That is the point worth keeping. Fault 5 had no endpoints at all, so
>> kube-proxy REJECTS the packet; fault 6 has an endpoint pointing at a
>> port nobody opened, so the pod refuses it. Two unrelated causes, one
>> indistinguishable client-side message. Anyone diagnosing this from the
>> error string alone would have declared fault 5 un-fixed and gone back
>> to re-checking labels. The endpoint list is what tells them apart.

--- INVESTIGATE ---

$ kubectl get endpoints task-api -n finalproject-broken
NAME       ENDPOINTS          AGE
task-api   10.244.1.24:8080   97s

$ kubectl get svc task-api -n finalproject-broken -o jsonpath='port: {.spec.ports[0].port}  targetPort: {.spec.ports[0].targetPort}{"\n"}'
port: 80  targetPort: 8080

$ kubectl get deploy task-api -n finalproject-broken -o jsonpath='containerPort: {.spec.template.spec.containers[0].ports[0].containerPort}  name: {.spec.template.spec.containers[0].ports[0].name}{"\n"}'
containerPort: 8000  name: http

--- ROOT CAUSE ---
  The endpoint is :8080; the container listens on :8000. targetPort was
  hard-coded to 8080 and matches nothing. Proof that the app is fine and
  only the Service's target is wrong:

$ GET / on the pod's REAL port, 8000
{"app": "task-api", "version": "1.0.0", "environment": "production", "hostname": "task-api-5dcdc9cfc-8wnms", "tasks": 0, "secrets_loaded": true}
>> The app answers. The Service was pointing at a port nobody opened.

--- FIX ---
  Fixed by NAME rather than by number. The container declares
  'name: http' on its port, so targetPort: http follows the container if
  the number ever changes -- the whole reason named ports exist.

$ kubectl patch svc task-api -n finalproject-broken --type=json -p='[{"op":"replace","path":"/spec/ports/0/targetPort","value":"http"}]'
service/task-api patched

--- VERIFY ---

$ kubectl get endpoints task-api -n finalproject-broken
NAME       ENDPOINTS          AGE
task-api   10.244.1.24:8000   103s
$ GET / through the Service DNS name
{"app": "task-api", "version": "1.0.0", "environment": "production", "hostname": "task-api-74d8d9564b-n6pzn", "tasks": 0, "secrets_loaded": true}
$ GET /ready
{"status": "ready"}
$ POST /tasks then GET /tasks
{"id": 1, "title": "all six faults fixed"}
{"tasks": [{"id": 1, "title": "all six faults fixed"}]}
