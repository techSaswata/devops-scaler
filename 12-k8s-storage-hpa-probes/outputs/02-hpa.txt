>> Without metrics-server, 'kubectl top' fails and every HPA reports
>> TARGETS <unknown>. It is the single most common reason an HPA does nothing.

>> NOTE for kind: metrics-server needs --kubelet-insecure-tls, because the
>> kubelet serving certs are not signed by the cluster CA. Without that flag
>> the pod runs but never becomes Ready.

=== 2. DEPLOY THE APPLICATION AND THE HPA ===

$ cat /Users/techsaswata/Downloads/devops-scaler/12-k8s-storage-hpa-probes/manifests/05-hpa.yaml | sed -n '1,30p'
# The workload the HPA will scale. php-apache burns CPU on every request, which
# is what makes the autoscaling observable.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hpa-demo
spec:
  replicas: 1
  selector: { matchLabels: { app: hpa-demo } }
  template:
    metadata: { labels: { app: hpa-demo } }
    spec:
      containers:
        - name: php-apache
          image: registry.k8s.io/hpa-example
          ports: [{ containerPort: 80 }]
          resources:
            # requests.cpu is MANDATORY for a CPU-based HPA: the target is a
            # PERCENTAGE OF THE REQUEST, so with no request there is nothing to
            # take a percentage of and the HPA reports <unknown>.
            requests: { cpu: 200m }
            limits:   { cpu: 500m }
---
apiVersion: v1
kind: Service
metadata:
  name: hpa-demo
spec:
  selector: { app: hpa-demo }
  ports: [{ port: 80, targetPort: 80 }]

--- why requests.cpu is mandatory ---

$ kubectl get deployment hpa-demo -o jsonpath='requests.cpu={.spec.template.spec.containers[0].resources.requests.cpu}{"\n"}'
requests.cpu=200m
>> averageUtilization: 50 means 50% OF THE REQUEST (200m), i.e. 100m per pod.
>> With no CPU request there is nothing to take a percentage of, and the
>> HPA can never compute a target.

  >> Scale-DOWN is deliberately slower than scale-up. Kubernetes defaults to a
  >> 300s stabilisation window so a brief dip in traffic does not destroy
  >> capacity you are about to need again. This manifest lowers it to 30s via
  >> spec.behavior.scaleDown.stabilizationWindowSeconds so the effect fits in a
  >> demo; leave the default in production.

  THE HPA ALGORITHM:

      desiredReplicas = ceil( currentReplicas x ( currentMetric / targetMetric ) )

  With 4 pods averaging 90% against a 50% target:
      ceil(4 x (90/50)) = ceil(7.2) = 8   -> capped at maxReplicas

  WHY AN HPA REPORTS <unknown>:
    1. metrics-server is not installed, or not Ready
    2. the container has NO resources.requests.cpu
    3. the pods are too new - give it ~30s after start
