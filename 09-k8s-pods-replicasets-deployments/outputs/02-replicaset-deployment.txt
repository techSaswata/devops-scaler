
=== 1. REPLICASET — desired state and self-healing ===

$ cat /Users/techsaswata/Downloads/devops-scaler/09-k8s-pods-replicasets-deployments/manifests/replicaset/backend-rs.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: backend-rs
  labels: { app: backend }
spec:
  replicas: 3                     # the DESIRED state
  selector:
    matchLabels:
      app: backend                # which pods this ReplicaSet owns
  template:                       # the Pod blueprint it stamps out
    metadata:
      labels:
        app: backend              # MUST match the selector above
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          resources:
            requests: { cpu: "20m", memory: "24Mi" }

$ kubectl apply -f /Users/techsaswata/Downloads/devops-scaler/09-k8s-pods-replicasets-deployments/manifests/replicaset/backend-rs.yaml
replicaset.apps/backend-rs created
replicaset.apps/backend-rs condition met

$ kubectl get rs backend-rs
NAME         DESIRED   CURRENT   READY   AGE
backend-rs   3         3         3       1s

$ kubectl get pods -l app=backend
NAME               READY   STATUS    RESTARTS   AGE
backend-rs-n7fzf   1/1     Running   0          1s
backend-rs-tj5bg   1/1     Running   0          1s
backend-rs-tx5h7   1/1     Running   0          1s
>> Pod names are <rs-name>-<random>. They are INTERCHANGEABLE.

--- SELF-HEALING: delete a pod and watch the controller replace it ---
$ kubectl delete pod backend-rs-n7fzf
pod "backend-rs-n7fzf" deleted from default namespace

$ kubectl get pods -l app=backend
NAME               READY   STATUS    RESTARTS   AGE
backend-rs-gpxhw   1/1     Running   0          6s
backend-rs-tj5bg   1/1     Running   0          7s
backend-rs-tx5h7   1/1     Running   0          7s
>> Still 3 pods. The ReplicaSet controller noticed actual(2) != desired(3)
>> and created a replacement. Note the NEW pod has a different name and AGE.
>> Compare with the bare Pod in module 08, which stayed deleted forever.

--- the link is the LABEL SELECTOR, nothing else ---

$ kubectl get rs backend-rs -o jsonpath='{.spec.selector.matchLabels}{"\n"}'
{"app":"backend"}
$ kubectl label pod <one-pod> app=orphaned --overwrite   (steal a pod from the RS)
pod/backend-rs-gpxhw labeled

$ kubectl get pods -L app
NAME               READY   STATUS    RESTARTS   AGE   APP
backend-rs-f86j5   1/1     Running   0          4s    backend
backend-rs-gpxhw   1/1     Running   0          10s   orphaned
backend-rs-tj5bg   1/1     Running   0          11s   backend
backend-rs-tx5h7   1/1     Running   0          11s   backend
>> Relabelling a pod ORPHANS it: the ReplicaSet no longer matches it, so it
>> creates yet another pod to get back to 3. The orphan keeps running,
>> now owned by nobody. Labels are the ONLY link between controller and pod.

$ kubectl scale rs backend-rs --replicas=5
replicaset.apps/backend-rs scaled

$ kubectl get rs backend-rs
NAME         DESIRED   CURRENT   READY   AGE
backend-rs   5         5         5       16s

$ kubectl delete rs backend-rs
replicaset.apps "backend-rs" deleted from default namespace

=== 3. ROLLING UPDATE ===

$ kubectl get deployment web -o jsonpath='{.spec.strategy}{"\n"}'
{"rollingUpdate":{"maxSurge":1,"maxUnavailable":1},"type":"RollingUpdate"}
>> maxUnavailable:1 = never more than 1 pod down.
>> maxSurge:1       = never more than 1 extra pod above the 4 desired.
>> Capacity therefore stays between 3 and 5 - so there is NO downtime.

=== 5. A FAILED ROLLOUT DOES NOT TAKE THE SERVICE DOWN ===
$ kubectl apply -f web-v3-broken.yaml   (image tag does not exist)
deployment.apps/web configured

$ kubectl get deployment web
NAME   READY   UP-TO-DATE   AVAILABLE   AGE
web    3/4     2            3           32s

$ kubectl get pods -l app=web
NAME                   READY   STATUS         RESTARTS   AGE
web-5dbb8cc686-bwkng   1/1     Running        0          27s
web-5dbb8cc686-nc4hs   1/1     Running        0          26s
web-5dbb8cc686-pwbmh   1/1     Running        0          27s
web-65b7ccb845-h49xw   0/1     ErrImagePull   0          25s
web-65b7ccb845-sf86f   0/1     ErrImagePull   0          25s
>> 2 new pods are stuck pulling an image that does not exist, but
>> 3 OLD pods are still Running and serving traffic.
>> That number is exactly replicas(4) - maxUnavailable(1) = 3: the rollout
>> is allowed to take down ONE healthy pod and no more, so it stalls here
>> instead of destroying the working release.

$ kubectl rollout status deployment/web --timeout=20s   (will report the stall)
Waiting for deployment "web" rollout to finish: 2 out of 4 new replicas have been updated...
error: timed out waiting for the condition

$ kubectl get rs -l app=web
NAME             DESIRED   CURRENT   READY   AGE
web-5dbb8cc686   3         3         3       52s
web-65b7ccb845   2         2         0       45s
web-665d78bc7b   0         0         0       50s

$ kubectl rollout undo deployment/web   (abandon the bad release)
deployment.apps/web rolled back
Waiting for deployment "web" rollout to finish: 3 of 4 updated replicas are available...
Waiting for deployment "web" rollout to finish: 3 of 4 updated replicas are available...
Waiting for deployment "web" rollout to finish: 3 of 4 updated replicas are available...
deployment "web" successfully rolled out

$ kubectl get pods -l app=web
NAME                   READY   STATUS    RESTARTS   AGE
web-5dbb8cc686-67tcm   1/1     Running   0          1s
web-5dbb8cc686-bwkng   1/1     Running   0          49s
web-5dbb8cc686-nc4hs   1/1     Running   0          48s
web-5dbb8cc686-pwbmh   1/1     Running   0          49s
>> Recovered. THIS is why you use a Deployment with a readiness probe.

$ kubectl delete deployment web
deployment.apps "web" deleted from default namespace
