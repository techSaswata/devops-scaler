
=== 1. MULTI-CONTAINER POD — the sidecar pattern ===

$ kubectl apply -f /Users/techsaswata/Downloads/devops-scaler/09-k8s-pods-replicasets-deployments/manifests/pods/multi-container.yaml

pod/multi-container condition met

$ kubectl get pod multi-container
NAME              READY   STATUS    RESTARTS   AGE
multi-container   2/2     Running   0          1s
>> READY 2/2 — two containers in ONE pod.

$ kubectl get pod multi-container -o jsonpath='{range .spec.containers[*]}{.name}{"\n"}{end}'
writer
web

--- the sidecar writes, the web container serves the same file ---

$ kubectl logs multi-container -c writer --tail=2

$ kubectl exec multi-container -c web -- cat /usr/share/nginx/html/index.html
<h1>Written by the sidecar — update #2</h1>

$ kubectl exec multi-container -c web -- curl -s http://localhost/
<h1>Written by the sidecar — update #2</h1>
>> They share a VOLUME (emptyDir) and a NETWORK namespace, which is why
>> the web container reaches its own port on plain localhost.

$ kubectl get pod multi-container -o jsonpath='{.status.podIP}{"\n"}'
10.244.2.13
>> ONE pod IP for both containers - that is the definition of a pod.

--- 4a. all three probes on a healthy pod ---

$ kubectl apply -f /Users/techsaswata/Downloads/devops-scaler/09-k8s-pods-replicasets-deployments/manifests/probes/probes.yaml
pod/probe-demo created
pod/probe-demo condition met

$ kubectl get pod probe-demo
NAME         READY   STATUS    RESTARTS   AGE
probe-demo   1/1     Running   0          4s

$ kubectl get pod probe-demo -o jsonpath='{range .spec.containers[0]}startup={.startupProbe.httpGet.path} readiness={.readinessProbe.httpGet.path} liveness={.livenessProbe.httpGet.path}{end}{"\n"}'
startup=/ readiness=/ liveness=/

  startupProbe    runs FIRST and alone; while it fails, the other two are
                  disabled. Gives a slow-booting app time WITHOUT weakening
                  the liveness probe forever.
  readinessProbe  "can this pod serve traffic right now?"
                  Failing -> removed from Service endpoints. NOT restarted.
  livenessProbe   "is this container wedged?"
                  Failing -> the kubelet KILLS and restarts the container.

=== 5. GRACEFUL TERMINATION — what 'kubectl delete pod' really does ===

$ kubectl apply -f /Users/techsaswata/Downloads/devops-scaler/09-k8s-pods-replicasets-deployments/manifests/lifecycle/termination.yaml
pod/lc-termination created
pod/lc-termination condition met

$ kubectl get pod lc-termination
NAME             READY   STATUS    RESTARTS   AGE
lc-termination   1/1     Running   0          0s

$ kubectl logs lc-termination
[app] started, serving traffic

$ kubectl delete pod lc-termination     (timing the whole shutdown)
pod "lc-termination" deleted from default namespace
deletion took 9s

--- what the container logged while it was shutting down ---
[app] started, serving traffic
[app] SIGTERM received — draining connections
[app] drained, exiting cleanly

>> The preStop hook ran, THEN SIGTERM arrived, THEN the app drained for 5s
>> and exited 0 on its own - it was never SIGKILLed. Total ~9s, well inside
>> the 30s grace period.

  THE SEQUENCE Kubernetes runs on delete:

    1. pod marked Terminating, and REMOVED FROM SERVICE ENDPOINTS
       (this happens first, so no new traffic is routed to it)
    2. the preStop hook runs
    3. SIGTERM is sent to PID 1
    4. Kubernetes waits up to terminationGracePeriodSeconds (30s here)
    5. still alive? SIGKILL

  Steps 2 and 3 share the same grace period - a preStop that sleeps longer
  than the grace period leaves no time for SIGTERM handling at all.

  WHY preStop EXISTS: endpoint removal is eventually consistent. Every
  kube-proxy has to be told. A short preStop sleep covers that window so
  in-flight requests are not sent to a pod that has already shut down.

  THE COMMON BUG: if your app runs under a shell wrapper, the shell is PID 1
  and SIGTERM never reaches your process - the pod is SIGKILLed after the full
  grace period every time. Use 'exec' in your entrypoint, or a tiny init.
