=== 3. SCA — pip-audit (CVEs in our DEPENDENCIES) ===
--- BEFORE remediation: the pin this project originally used ---
$ pip-audit -r <Flask==3.0.3>
Found 2 known vulnerabilities in 1 package
Name  Version ID              Fix Versions
----- ------- --------------- ------------
flask 3.0.3   PYSEC-2026-2151 3.1.3
flask 3.0.3   PYSEC-2026-2151 3.1.3

>> A REAL finding: PYSEC-2026-2151 in Flask 3.0.3, fixed in 3.1.3.
>> Flask omits the 'Vary: Cookie' header on some session access patterns,
>> so a caching proxy can serve one user's page to another.

--- AFTER remediation: the pin now committed ---

$ cat requirements.txt
Flask==3.1.3

$ /tmp/cicdvenv/bin/pip-audit -r requirements.txt 2>&1 | tail -3
No known vulnerabilities found
>> Clean. This is the whole point of SCA: the vulnerability was not in
>> code we wrote, and no amount of code review would have found it.
>> SAST checks code WE wrote; SCA checks code we DEPEND ON. Most real
>> vulnerabilities in an application come from the second category.

=== 7. THE SECURITY GATE ===
  The gate is STRUCTURAL, not advisory. In the workflow:

      push:
        needs: [security-gate]

      security-gate:
        needs: [test, sast, sca, secret-scan, image-scan]

  GitHub will not start `push` unless every one of those jobs succeeded, so
  there is no path by which a failing scan still ships an image.

  Compare with the common anti-pattern:

      - run: trivy image myapp || true        # <- reports, never blocks

  which produces a dashboard nobody acts on.

  WHERE EACH CONTROL SITS

    SAST          our code            before anything is built
    SCA           our dependencies    before anything is built
    Secret scan   our repository      including full git history
    Image scan    the built artifact  after build, BEFORE push
    Config scan   our manifests       after push, before deploy
