
==================== 1. IMPERATIVE vs DECLARATIVE ====================
IMPERATIVE — you tell Kubernetes WHAT TO DO, step by step:

$ kubectl run nginx-imperative --image=nginx:1.27-alpine
pod/nginx-imperative created

$ kubectl get pod nginx-imperative
NAME               READY   STATUS              RESTARTS   AGE
nginx-imperative   0/1     ContainerCreating   0          0s

>> Fine for a quick test. But there is no file, so nothing is reviewable,
>> version-controlled or repeatable.

DECLARATIVE — you describe the DESIRED STATE in a file and apply it:
$ cat manifests/first-pod.yaml
# The smallest useful Pod: one container, declared rather than commanded.
apiVersion: v1                 # core API group
kind: Pod                      # what to create
metadata:
  name: hello-pod
  labels:
    app: hello                 # labels are how Services and ReplicaSets find pods
spec:
  containers:
    - name: web
      image: nginx:1.27-alpine
      ports:
        - containerPort: 80    # documentation; it does not publish anything
      resources:
        requests:              # what the SCHEDULER reserves for this pod
          cpu: "50m"
          memory: "32Mi"
        limits:                # what the kubelet ENFORCES at runtime
          cpu: "200m"
          memory: "128Mi"

$ kubectl apply -f /Users/techsaswata/Downloads/devops-scaler/08-kubernetes-fundamentals/manifests/first-pod.yaml
pod/hello-pod created

>> This is the form that belongs in git, and the form to use everywhere.
>> 'apply' is idempotent - run it twice and the second is a no-op:

$ kubectl apply -f /Users/techsaswata/Downloads/devops-scaler/08-kubernetes-fundamentals/manifests/first-pod.yaml
pod/hello-pod unchanged
>> 'unchanged', not 'created' - Kubernetes diffed it and found nothing to do.

$ kubectl exec hello-pod -- curl -s -o /dev/null -w 'self HTTP %{http_code}\n' http://localhost

--- port-forward: reach a pod from the host without any Service ---
$ kubectl port-forward pod/hello-pod 18080:80 &

HTTP 200
>> Useful for debugging. NOT a substitute for a Service (module 10).

==================== 7. THE RECONCILIATION LOOP — the single most important idea ====================
A bare Pod has NO controller watching it. Delete it and it stays dead:

$ kubectl delete pod nginx-imperative
pod "nginx-imperative" deleted from default namespace

$ kubectl get pods
NAME        READY   STATUS    RESTARTS   AGE
hello-pod   1/1     Running   0          5s

>> 'nginx-imperative' is gone for good. Nothing is reconciling it.
>> That is precisely why you use Deployments instead of bare Pods -
>> demonstrated in module 09.

==================== 8. NAMESPACES IN PRACTICE ====================

$ kubectl create namespace demo
namespace/demo created

$ kubectl run ns-test --image=nginx:1.27-alpine -n demo
pod/ns-test created

$ kubectl get pods -n demo
NAME      READY   STATUS              RESTARTS   AGE
ns-test   0/1     ContainerCreating   0          1s

--- the same name can exist in two namespaces without colliding ---

$ kubectl get pods --all-namespaces -l run=ns-test
NAMESPACE   NAME      READY   STATUS              RESTARTS   AGE
demo        ns-test   0/1     ContainerCreating   0          1s

--- objects are invisible across namespaces unless you ask ---

$ kubectl get pods | grep ns-test || echo '(not visible in the default namespace)'
(not visible in the default namespace)

$ kubectl delete namespace demo
namespace "demo" deleted
>> Deleting a namespace deletes EVERYTHING inside it. Handle with care.
